# AGENTS — вход в User

**До любого изменения кода или UI:**

1. Прочитай `PROJECT_STATE.md` в **текущем репозитории**.
2. Прочитай **единый UI-контракт**: [co-va/core/staging/UI_ALPHABET.md](https://github.com/co-va/core/blob/staging/UI_ALPHABET.md). Это **единственный** нормативный источник идентификаторов, владельцев и межрепозиторных правил UI. Не создавай локальную копию или вторую карту.
3. Для F/E/режимов/capabilities и владельцев данных прочитай [co-va/core/staging/BUSINESS_ARCHITECTURE.md](https://github.com/co-va/core/blob/staging/BUSINESS_ARCHITECTURE.md). Для тарифных прав отдельно читай [COMMERCIAL_TARIFF_CONTRACT.md](https://github.com/co-va/core/blob/staging/COMMERCIAL_TARIFF_CONTRACT.md); не путай статус готовности инструмента с приёмкой визуального UI.
4. Для технической приёмки Professional обязательно прочитай его [RELEASE_CLOSURE_MAP.md](https://github.com/co-va/professional/blob/staging/RELEASE_CLOSURE_MAP.md) и [RELEASE_CLOSURE_REGISTRY.json](https://github.com/co-va/professional/blob/staging/RELEASE_CLOSURE_REGISTRY.json). Не объявляй их статусы статусами User или Admin.
5. Перед изменением общего компонента установи его ID из UI_ALPHABET, **реального владельца исходника**, места использования в остальных приложениях и утверждённую форму. Если источники недоступны — явно укажи ограничение; ничего не угадывай.
6. **Scope:** User UI resides here; the four owner-approved Shared UI corrections dated 2026-11-13 are implemented in `user/staging` and released through the normal `staging → main` PR gate. After release, the **owner-designated canonical Shared UI reference is `co-va/user/main`**, checked against the released SHA and tests, while `staging` remains the development branch. See `PROJECT_STATE.md` and `CI_CONTRACT.md`. This design reference alone does not prove every User feature accepted on a device. Do not change Core or Professional. Изменяй только разрешённый репозиторий и `staging`. Не трогай `main`, чужой код, защитные тесты и утверждённый UI без явного разрешения. Не создавай новый план вместо продолжения существующего.

**Перед межрепозиторной синхронизацией:** для `shared.modal`, `shared.input`, `shared.selector`, `shared.shell` сначала прочитай раздел о четырёх правилах в `PROJECT_STATE.md`, затем **живой `co-va/user/main`**; сравни релизный SHA и результаты CI. Не принимай ещё не выпущенный `staging` за нормативный эталон. Не переносить старые 14/18/20/22 px и 48/52 px полей. Нормативный `UI_ALPHABET.md` остаётся только в Core; этот файл его не заменяет.

**Завершение:** сообщи точно, что изменено, что проверено, что не проверено, SHA/PR и статус реальной приёмки. Нельзя называть компонент «утверждённым» по одному зелёному тесту.

`AGENTS.md` — точка входа для исполнителя, **не** автоматическая блокировка GitHub. Защиту обеспечивают отдельные реальные проверки и настройки репозиториев.

**Фиксация работы и выпуск:** перед работой читать [BUSINESS_ARCHITECTURE §18.2](https://github.com/co-va/core/blob/staging/BUSINESS_ARCHITECTURE.md#182-защита-выпуска-в-main--решение-владельца-24112026). После изменения фиксировать `Operational-Evidence` в Git по точным путям и существующим ID критериев; формат и пример — `CI_CONTRACT.md`. Для PR в main это часть обязательного `check`. Не копировать центральный скрипт и карту, не подменять приёмку владельца записью о разработке. Не изменять main без разрешения.

**Личное разрешение владельца:** защищённые пути перечислены в `.github/CODEOWNERS`. Работать под отдельным исполнителем `3001vaf-maker`; владелец `co-tools` подтверждает изменения сам. Не выполнять Review от лица владельца и не обходить защиту. Для main действует ruleset, а не обещание в чате. См. CI_CONTRACT.md.

**Проверка личности перед записью в GitHub:** перед первым изменением в каждом новом чате проверить фактический логин подключения. Запись в репозиторий разрешена только от `3001vaf-maker`; если активен `co-tools` или иной аккаунт, остановить изменения и сообщить владельцу. Подтверждение архитектурного PR выполняет владелец лично в GitHub, не через чат. Не считать разрешением на слияние наличие зелёного CI или отсутствие конфликтов.

**Обязательное личное подтверждение владельца:** если PR требует Code Owner review, сразу отправь владельцу в текущем чате прямую кликабельную ссылку на конкретный PR (`https://github.com/co-va/<repo>/pull/<номер>`), название репозитория, кратко что меняется и инструкцию: «Открыть ссылку → Review changes (при необходимости Files changed) → Approve → Submit review». Не отправляй владельца самостоятельно искать PR. После его сообщения о подтверждении проверь через GitHub Review APPROVED от `co-tools` для актуального head SHA, обязательные CI и отсутствие блокировок. Если требуется повторное подтверждение после новых коммитов, снова пришли прямую ссылку. Не выполняй Review от имени владельца, не обходи защиту и не сливай без требуемого подтверждения. Обычные изменения вне защищённых путей не требуют личного Review, если GitHub его не требует; остальные разрешения на выпуск сохраняются.
