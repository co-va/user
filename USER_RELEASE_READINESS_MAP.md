# USER — карта бизнес-готовности и аудит дублирования

**Дата:** 13.11.2026  
**Область:** только `co-va/user`. Эталон, с которого начат аудит: `main = staging = ba8334c9f733ce5ac3aec6c5b0cc82ef2da3163f`.  
**Нормативные источники:** `co-va/core/staging/BUSINESS_ARCHITECTURE.md`, `COMMERCIAL_TARIFF_CONTRACT.md`; готовность инструментов управляется в Core через `AdminToolReadiness`, **не** определяется процентом тарифа.  
**Границы:** серверную БД и бизнес-логику `co-va/core` аудит не меняет; реальные платежи/согласия/записи не создавались; это аудит реализации User и имеющихся CI.

## Решение для владельца

**Статус на момент аудита: три основные карты — «В проверке», «Интеграции» — отдельно отложены.** Ставить всем остальным «Готово» только после закрытия блокеров и приёмочных сценариев ниже. UI владельцем уже выборочно проверен («запись» и «событие» созданы успешно), но это не доказывает отсутствие повторов и изоляцию данных.

| Карта User | Что входит в проверку | Доказательства | Готовность |
| --- | --- | --- | --- |
| **Профиль** | регистрация/вход/выход, сохранение полей, фото, Email, документы, согласия, Push | `User / Profile` CI, keyboard и Email smoke. Реальный переключатель аккаунтов и независимый статус Email не принят владельцем как сквозной тест | **В проверке** |
| **Журнал** | День/Месяц/Список, записи/повтор, события и заметки CRUD, уведомления, отсутствие повторных PUT/POST и лишних GET | `User / Record`, `user-journal-record-smoke`, ручное создание записи и события. Обнаружены два дефекта изоляции/прочтения, на staging внесены исправления с новыми тестами | **В проверке** |
| **Контакты** | поиск, привязка/удаление связи, согласие на запись, пространства, история, депозиты/счета, карты/скидки | Реальные API-адаптеры, `User / Profile`, `User / Check`, в истории записи объединяются по ID. Нет полного независимого сквозного теста всех финансовых/согласительных вариантов | **В проверке** |
| **Интеграции** | Google/Яндекс календарь, подключения, экспорт/синхронизация/отключение | UI и адаптеры есть; внешние OAuth/пароли/экспорт и тяжёлую синхронизацию сейчас целенаправленно **не принимаем** | **Отложено (последняя карта)** |

*У User сейчас четыре F-карты: Профиль, Журнал, Контакты, Интеграции. После приёмки первых трёх можно считать 3 из 4 карт готовыми; **75% — только счётчик карт**, не взвешенная бизнес-готовность и не статус в Admin.*

## Что найдено в коде (не предположения)

### Без лишнего дублирования: существующие механизмы

- **Создание записи:** `user/record-flow.js` ставит `recordsBusy`, блокирует кнопку до ответа; `core/record/platform-api.js` отправляет один POST на подтверждение. UI защищён от двойного нажатия. Серверную идемпотентность запроса при обрыве связи в Core этим **не доказали**.
- **Списки записей:** `core/account/index.js:getGlobalAccountRecords()` объединяет одновременные запросы в один Promise и привязывает их к токену. `user/main.js` объединяет последовательные обновления через `refreshPromise` и минимальный интервал 1 сек.
- **Контакты и цели записи:** `user/app.js:loadRelationships()` использует один незавершённый Promise; `core/record/platform-api.js:getRecordContacts()` также объединяет конкурентные запросы по токену.
- **Журнал:** история удалённых записей загружается единожды за монтирование журнала; смена вида Списка не повторяет GET. В истории пространства `getGlobalContactWorkplaceHistory()` собирает одну карту записей по ID, чтобы два источника не породили дубль.
- **UI:** один общий MiniCard, одна семья Compact 28×28; `User / Shared UI` и `User / Repository` контролируют JS/CSS владельцев. Это не заменяет проверку данных.

### Дефекты, выявленные этим аудитом

| ID | Приоритет | Наблюдение и источник | Решение / статус |
| --- | --- | --- | --- |
| U-A01 | **Критично** | `core/event/account-owner.js` и `core/note/account-owner.js` хранили глобальные `rows/loaded/loading`, не привязанные к аккаунту. После входа другим человеком на той же странице мог отображаться предыдущий кэш; запоздалый GET мог вернуть старые данные | Общий `core/account/session-cache.js`, сброс/изоляция при смене токена/выходе, проверка эпохи ответов. Добавлен `user-account-session-smoke.mjs` |
| U-A02 | **Высокий** | `core/notifications/service-unseen.js` считывал `data-user-journal-record` как обычный ID, хотя журнал передаёт JSON `[tenantId, recordId]`. При открытии записи сигнал «непрочитано» мог не сброситься | Единое извлечение составного ключа, сверка tenantId, один запрос отметки о прочтении; браузерная проверка в `user-journal-record-smoke.mjs` |
| U-A03 | **Оценить отдельно** | `renderDay` вызывает `syncAccountCalendars()` при создании отображения дня. | U-A04 | **Внешний блокер** | После merge PR #24 проверка доступности `https://user.va-tools.ru/` дважды упала: 3/5, затем 4/5 запросов HTTPS завершились сетевыми тайм-аутами. Отдельная браузерная проверка открытия входа завершилась PASS | Нужна стабильная production availability/HTTPS проверка. Нельзя назвать доступность безусловно готовой |

### Не доказано без реального Core/API (отдельная проверка)

- **Повтор/подтверждение записи:** конкурентное создание (двойной клик, вкладки и повтор после сетевого тайм-аута); конфликты слотов, занятость по рабочему пространству, запрещённое прошедшее время. Фронт блокирует повторный клик, но атомарность серверной записи принадлежит Core.
- **Данные записи:** фиксирование суммы/скидки на момент записи, предоплата/долг, статусы «пришёл/не пришёл», отмена и сохранение удалённой истории — нужны тестовые API-ответы и роль со связанным пространством.
- **Контакты:** корректность видимости контактов/пространств, согласий и истории при разных организациях, удаление связи без удаления серверных фактов, реальные данные программ/депозитов.
- **Профиль и уведомления:** вход другого аккаунта без перезагрузки, отсутствие «чужих» пушей/меток и лишних фоновых загрузок после выхода.
- **Продуктивность:** один GET на журнал при первом входе, отсутствие повторных GET при День↔Месяц↔Список, тайминги открытия Z/Q на iPhone. Тесты измеряют некоторые сценарии, но не полную матрицу на устройстве.

## Карта приёмки: что должно стать PASS перед «Готово»

| Контроль | Приёмочный сценарий | Тип доказательства |
| --- | --- | --- |
| G1 Сессии | Вход А → создание события/заметки → выход → вход Б **без обновления страницы**; Б не видит данные А. Задержанный ответ А не может изменить данные Б | Node session smoke + браузер с двумя тестовыми аккаунтами |
| G2 Запись | Создание, повтор, быстрая двойная попытка, истёкшая/занятая ячейка; **одна** созданная запись и один POST в штатном сценарии | Browser smoke + серверные логи Core |
| G3 Журнал | День/Месяц/Список; запись/событие/заметка не дублируются, отменённые и удалённые отображаются по договорённости | Browser smoke + ручная проверка |
| G4 События/заметки | Создать → изменить → закрыть/переоткрыть → удалить; нет повторных элементов или сохранений | Node/browser smoke + тестовый Core |
| G5 Уведомления | Открытие элемента с составным ключом сбрасывает только его непрочитанную отметку, **один** запрос seen | Browser smoke |
| G6 Контакты | Поиск, привязка с согласием, 2 пространства, история, повтор, депозиты/личный счёт, корректное разделение организаций | API-браузер на тестовых данных |
| G7 Профиль | Правка, Email подтверждение, согласия, выход/возврат, Push; нет второго модала и чужого состояния | Browser + iPhone |
| G8 Загрузка/сеть | Счётчики запросов по входу, открытию разных экранов и переключению вида; убрать избыточные дубли, не отключая необходимые актуализации | Network trace браузера/CI |
| G9 Продакшен | HTTPS HTML, версия JS/CSS и runtime вход стабильны; обязательные проверки зелёные | GitHub Actions + проверка устройства |
| G10 Интеграции | Провайдеры, подключение/отключение, sync/export и повторные POST | **Отложено по решению владельца** |

## Порядок закрытия

1. Принять на `user/staging` исправления U-A01/U-A02 и их регрессионные тесты (код User, не `co-va/core`).
2. Закрыть G1–G9; тестировать реальные операции только на специально отведённых тестовых данных, без воздействия на настоящие записи.
3. После успешных проверок владелец может перевести **Профиль, Журнал, Контакты** в «Готово» в административном реестре Core. **Интеграции** остаются «В проверке»/«Не готово» до отдельной задачи; их статус и тарифы независимы.
4. Выпуск через `staging → PR → main` — отдельное утверждение. Не исправлять UI или другие репозитории в ходе этого аудита.

**Важно:** эта карта — реестр доказательств и незакрытых сценариев, а не дополнительный UI-контракт, не автоматическая команда переключения статуса и не подтверждение стабильности production.
